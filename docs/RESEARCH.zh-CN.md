# LeafVault 调研依据与待验证问题

核查日期：2026-10-20。以下来自项目官方网页、官方仓库和技术文档；产品状态和许可政策可能随版本变化。尚未执行竞品实机对照、用户访谈或 LeafVault 技术实验。

## 1 现有产品

| 产品 | 本次核查到的事实 | 对 LeafVault 规划的启发 |
| --- | --- | --- |
| Obsidian | 官方软件个人与商业使用免费，Sync 与 Publish 是可选付费服务 | 仅有“免费”不足以形成差异；完整开源和自托管体验需要具体实现 |
| Logseq | 官方仓库介绍数据库版本及新的同步方式，并区分相应测试阶段 | 不能沿用“所有版本都是普通 Markdown 文件”的旧概括；比较时必须记录版本与数据模型 |
| 思源笔记 | 官方说明完整开源、支持 Docker；部分能力属于付费会员；正文使用 `.sy` JSON 文件 | 开源、免费功能范围、自托管和原生 Markdown 是不同维度，应分别核对 |
| Joplin | 官方同步文档列出 Nextcloud、S3、WebDAV、Dropbox、OneDrive、本地文件系统等目标 | 可借鉴不锁定单一同步服务的思路；适配多后端并不自动解决冲突 |
| SilverBullet | 官方 FAQ 区分 MIT 开源 Server 与未开源的 Desktop | 核对整个产品链路的许可，不能仅从服务端开源推断桌面端也开源 |

来源：

- [Obsidian 价格与免费范围](https://obsidian.md/pricing)
- [Logseq 官方仓库及数据库版本状态](https://github.com/logseq/logseq)
- [思源官方仓库、功能与存储 FAQ](https://github.com/siyuan-note/siyuan)
- [Joplin 同步文档](https://joplinapp.org/help/apps/sync/)
- [SilverBullet 官方 FAQ](https://silverbullet.md/faq)

这些事实说明已有产品覆盖了许多目标能力，不能据此声称市场存在无人解决的空白。LeafVault 的选择是把“完整开源、官方软件无功能付费墙、普通 Markdown、桌面输入体验、自托管同步”作为一组共同约束，随后用真实任务验证价值。

## 2 新建项目与复用方案

| 路径 | 收益 | 主要代价 |
| --- | --- | --- |
| 为现有项目贡献 | 现成社区、功能和发布链路 | 数据模型、产品政策和路线需要与上游一致 |
| Fork 一个现有项目 | 能继承部分成熟能力 | 长期合并上游、理解已有架构与维护分叉的成本 |
| 新建客户端，复用编辑器等通用组件 | 能直接落实文件与体验原则 | 保存、兼容、同步与分发仍需完整验证 |

当前建议第三条路径：独立实现客户端及有限范围的同步服务，使用成熟通用组件。正式写应用前，P01–P05 仍应检查是否有可直接复用或向上游贡献的方案；若能显著减少长期维护成本，可以调整决定。

不计划重写底层文本编辑器、密码学原语或数据库。同步协议的工程成本需要被明确计算，不能因为 API 较少就认为同步简单。

## 3 技术依据

- [Tauri 概览](https://v2.tauri.app/start/)：说明系统 WebView 和架构选项；不支持对 LeafVault 包体或内存作出未经测量的承诺。
- [Tauri WebView 文档](https://v2.tauri.app/reference/webview-versions/)：不同平台依赖不同运行时，应分别验证输入与渲染。
- [CodeMirror 官方网站](https://codemirror.net/)与[开发仓库迁移说明](https://github.com/codemirror/dev)：作为文本编辑器候选；具体版本和扩展兼容性在 M1 核查。
- [SQLite FTS5](https://www.sqlite.org/fts5.html)：作为全文索引候选；中文短词不能靠未测量的默认配置保证。
- [GNU 对 AGPL 的解释](https://www.gnu.org/licenses/why-affero-gpl.en.html)与[AGPL 许可说明和全文](https://choosealicense.com/licenses/agpl-3.0/)：用于确定源码开放政策；官方软件是否收费另由项目政策确定。

服务端 Rust/Axum、React 界面及具体状态格式是本项目的候选工程选择，不是以上来源已经验证的 LeafVault 方案。真正使用前需核对依赖维护状态、许可和版本。

## 4 待验证的问题

| 问题 | 验证方法 | 改变计划的条件 |
| --- | --- | --- |
| 用户会为了开源与自托管迁移吗 | 3–5 个真实工作流、迁移演练、7 天试用 | 没有持续使用意愿，先缩小目标用户或重新定位 |
| 手机是不是不可缺少的首版条件 | 分开询问电脑写作与手机记录频率 | 大多数目标用户必须手机可用，重新估算移动端优先级 |
| Markdown 即时预览是否足够好用 | 中文输入和选区样例、现有编辑器对照 | 无法稳定保留输入状态，调整渲染或外壳方案 |
| 只支持常用语法能否完成迁移 | 真实库副本扫描与功能依赖清单 | 核心工作流依赖未覆盖语法，缩小兼容承诺或补齐能力 |
| 自托管是否足够容易 | 未参与开发者执行部署与恢复说明 | 多次需要手工介入，先改文档与部署体验 |
| 首版信任服务器的模型是否可接受 | 明确说明管理员可读内容，询问使用场景 | 目标用户依赖不可信服务器，端到端加密需提前 |

工作量和性能数字均为规划假设，见 [路线图](ROADMAP.zh-CN.md)。完成实验后把结果与对应提交号补入文档，不把计划直接改写为已验证事实。
