# LeafVault 自托管同步方案

日期：2026-10-20。状态：设计草案；不存在可部署服务。

首版目标是一个人将多个桌面设备连接到自己控制的服务器。正文和附件先保存在本地，网络恢复后交换已提交的变化。同步包括冲突与恢复，是首版产品的重要组成部分。

## 1 首版边界

支持单个所有者、多设备、多笔记库、离线编辑、增量传输、设备撤销、版本历史和备份恢复。服务只部署在一个节点，数据库和附件均在该节点持久化。

多人实时协作、跨服务器联邦、高可用集群及 WebDAV/S3 客户端直连另行设计。首版选择专用服务，是为了把版本、冲突、删除和恢复定义清楚；自托管并不意味着一定要用 WebDAV。

移动端稍后接入同一协议，但不能把移动操作系统后台限制视作已经解决。

## 2 部署与连接体验

部署目标：

- 一个应用容器，包含 API、管理入口和数据库访问逻辑。
- 一个持久化数据目录，包含 SQLite 元数据、不可变内容块和恢复所需日志。
- 通过现有反向代理提供 HTTPS；需要时提供额外的反向代理示例。完整公网部署可能有多个容器。
- 首次启动创建所有者，不提供默认口令；设备通过一次性、短时有效的配对流程加入。
- 服务提供版本、健康状态、磁盘用量、设备列表、备份时间和运行源码的入口。
- 不需要项目方云账号，不回连项目方的授权服务。

部署说明应覆盖主机前提、文件权限、持久化卷、TLS、首次配对、升级、回退及迁移。不会用一个尚不存在的 `docker run` 命令声称部署完成。

验收目标：在已准备好 Docker 和有效 HTTPS 入口的主机上，首次使用者按文档在 30 分钟内连接两台设备。域名准备、证书申请和镜像首次下载耗时另外记录，不混入此目标。

## 3 协议需要保证的性质

| 性质 | 设计要求 |
| --- | --- |
| 顺序明确 | 服务端分配单调递增的变更序号，不依赖设备时间排序 |
| 重试安全 | 每个操作有持久化的设备 ID 与操作 ID；重试同一操作返回同一结果 |
| 防止覆盖 | 写入带预期基线版本；基线不符时拒绝直接覆盖并进入冲突流程 |
| 删除可传播 | 删除保存专门记录，不能仅靠“本地文件不存在”推断远端应该删除 |
| 重命名可追踪 | 同步对象 ID 与路径分开；应用内重命名保留对象 ID |
| 传输完整 | 内容按哈希验证，上传完成前不发布引用该内容的新版本 |
| 库之间隔离 | 每次请求检查设备对笔记库的权限，不能凭内容哈希下载其他库的对象 |
| 协议可升级 | 明确协议版本和最小兼容版本；不兼容时保留本地内容并停止同步 |

本地状态至少包括对象 ID、路径、基线版本、内容哈希、待发操作、已应用游标和恢复日志。服务端至少包含当前版本、历史、删除记录、设备授权与游标范围。

内容文件和数据库的持久化顺序必须可恢复：先持久化不可变内容，再在数据库事务中提交版本、去重结果和变更日志。垃圾回收不能删除仍被当前版本、有效历史或备份引用的内容。

## 4 一次同步的目标流程

1. 本地编辑先按保存协议持久化，操作进入可靠的待发队列。未联网时不阻塞继续写作。
2. 拉取上次游标后的变更，逐项核对本地基线、未发送编辑和文件实际状态。
3. 没有本地分歧的更新可以应用；应用结果持久化后才能推进游标。中途崩溃重放不得重复损坏文件。
4. 上传必要内容块，再提交带基线版本及操作 ID 的操作。客户端不会在确认结果前移除待发内容。
5. 请求超时后，查询或重试同一操作 ID。不能因为“没有收到响应”就另建操作。
6. 远端又发生变化时，重新拉取并进行版本检查。合并、冲突解决和恢复都会生成可追踪的新版本。

操作队列的压缩、部分失败、批量重命名和中断续传均需要明确规范后才能实现；不能通过压缩队列丢失尚未确认的删除或冲突内容。

## 5 冲突规则

首版默认保留两份内容并让用户处理，不以“最后修改时间获胜”覆盖另一份，也不自动合并有歧义的文字。

| 情况 | 预期行为 |
| --- | --- |
| 两台设备修改同一基线 | 一份成为已提交版本；另一份保存为稳定命名的冲突副本，提示比较和选择 |
| 一台删除、另一台编辑 | 保留编辑内容与删除记录，提供恢复或确认删除的选择 |
| 一台重命名、另一台编辑 | 能明确识别同一对象时沿对象 ID 保留编辑；路径冲突时保留内容并提示 |
| 两台设备各创建同名笔记 | 保留两个不同对象，为冲突项分配稳定的新路径，不静默覆盖 |
| 同一附件出现不同内容 | 按不同对象保存两份，维护各自引用；不对二进制内容做文本合并 |
| 外部编辑器发生改动 | 先比较哈希与本地基线；同步不能覆盖未识别的外部编辑 |
| 外部文件被移动 | 只有在身份可确定时按重命名处理；不确定时作为删除与新建并保留恢复记录 |
| 设备时间相差很大 | 仍由服务端序号和基线版本判断；时间只用于展示 |

冲突副本根据原对象和操作 ID 稳定标识；重复同步不会每次制造一份新副本。冲突需要跨设备可见，用户确认解决后才能清除对应提示。

重命名涉及其他笔记中的链接更新时，每个文件分别遵守基线检查。发生部分成功要记录并恢复，不能宣称跨多份 Markdown 文件天然原子。

## 6 删除保留与长期离线设备

正文历史初始目标为保留 30 天，管理员可以调整；未解决冲突和未确认操作不能被历史清理顺带移除。历史保留天数不直接决定删除记录的清理时机。

删除记录在活跃设备确认之前保留。撤销设备或压缩旧变更后，游标过期设备必须重新对账，先展示本地独有内容与远端删除差异；禁止把旧文件库当作全新内容自动上传，造成已删除笔记复活。

重新对账需要服务器返回完整的有效对象清单和同步世代。服务端从旧备份恢复时更换世代，客户端检测后保留本地数据进入恢复流程，不继续沿用旧游标。

## 7 历史、备份与服务器迁移

同步会传播误删，所以备份需要与同步分开设计。

- 本地提供最近版本与误删恢复入口；恢复产生新版本，原有历史仍可查。
- 服务端备份必须得到一致的数据库快照及其引用的内容块，不能只随意复制活动数据库文件。
- 备份清单包含协议版本、数据库格式版本、内容校验和以及必要的身份和配置恢复材料；凭据按独立的保密策略处理。
- 先备份再执行数据库迁移；不兼容的升级通过恢复备份回退，不能直接用旧程序打开新格式。
- 提供迁移到新服务器的流程：验证备份、恢复、核对内容、重新确认设备连接。
- 首版验收假设每日备份一次，以最多 24 小时的备份间隔和 60 分钟内完成测试库恢复为演练目标；这不是所有部署的恢复保证。

所有恢复演练在空白实例进行。逐文件哈希、对象数量、版本关联和附件可读性都要核验，不能只检查容器能启动。

## 8 隐私与访问控制

首个同步版本采用“信任自托管服务器”的模型：HTTPS 保护传输，服务器管理员能够访问正文、文件名和附件。服务端磁盘加密也不等同于端到端加密，产品界面与文档必须明确这一点。

端到端加密是后续独立里程碑，需要覆盖密钥生成、设备加入、恢复密钥、撤销后换钥、历史迁移和泄漏的元数据范围。未经实现与验证，不宣称服务器无法读取内容。

首版至少要求设备级可撤销凭据、短期配对凭据、请求限额、上传大小限制、库权限检查、日志脱敏以及安全的路径处理。资源限制应可由管理员调整，并清楚标为运行限制，不作为付费分层。

撤销设备阻止未来访问，不会远程抹掉已经下载到该设备的内容。

## 9 上线前故障验证

M3 必须覆盖断网、响应丢失、重复请求、提交后崩溃、磁盘满、附件上传中断、并发同名、编辑与删除冲突、外部编辑、旧设备重连、设备撤销及备份回退。

各场景需要有固定输入、故障注入位置、预期文件与版本状态、重放步骤和实际核验结果。无丢失和稳定收敛是发布门槛；通过少量顺序上传演示不代表同步可靠。
